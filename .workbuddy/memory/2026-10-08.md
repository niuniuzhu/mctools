## 🔴 重大发现：临时库回退的真凶不是数据库锁，而是删除保护
- **之前判断错了**：一直以为 3004 回退到 TEMP 库是因为真库被兄弟实例锁住（多进程抢库）。**实际不是**——真库在 WAL 模式下多进程共享完全可写（实测 `BEGIN IMMEDIATE` 探测成功）。
- **真正原因**：`server.js` 的 `canUseDirectory(dirPath)` 写完探测文件后要 `fs.unlinkSync(probePath)` 删除它，但本机环境的删除保护（safe-delete走回收站/genie-trash）会拦截并抛异常 → 被外层 `catch` 吞掉 → 返回 `false` → `resolveWritableDatabasePath()` 直接跳到下一个候选（临时库）。**数据库本身完全正常，纯粹是"删探测文件"这一步被环境策略挡住。**
- **修复**：`canUseDirectory` 里把 `fs.unlinkSync(probePath)` 包进独立 try/catch，删除失败不再影响可写性判断（写入成功即代表目录可用，残留探测文件是可忽略的临时文件）。改完 3004 立即连上真库。
- **验证方式**：`grep "SQLite database path" 日志` 应为 `D:\Projects\mctools\data\users.db`。
- **排查同类问题的通用套路**：数据库明明可写却仍回退时，不要只看数据库锁，要单独跑一遍 `canUseDirectory` 的逻辑（写探针 + 删探针）看是哪一步抛错。删除类操作在本机会被 safe-delete 拦截，报错形如 `Error during a 'trash' operation`。
- **附带影响**：同一原因下 `data/` 目录曾被判为不可写，日志里不报错（被 catch 吞了），非常隐蔽——`resolveWritableDatabasePath` 里的回退是静默的。
- 数据已统一到真库：迁移了临时库的今日签到记录，`星际Stellar（开发者）` 积分 10、今日(10-08)已签到、连续 2 天、SVIP 正常显示。临时库备份留在 `data/users.db.temp-backup`。
- 注：本机 `wmic` 被系统级工具策略禁用、`Get-CimInstance` 返回空，查进程启动参数较困难；改用 `netstat`+`tasklist` 组合定位端口↔PID。

## 修侧边栏「按钮飘到九霄云外」：定位锚点错误
- **Bug 根因**：`.side-dock` 用了 `top:50% + transform: translateY(-50%)` 做垂直居中。translateY(-50%) 按**元素自身高度**计算，而展开后容器高度从 ~50px 涨到 ~300px → 偏移量随之翻倍 → 整个侧栏被推到视口上方外侧，看起来"飘走了"。
  - **教训：「居中 + 内容会变高」的场景不能用 translateY(-50%)**，内容一变高偏移就失控。
- **修复（3 处配合）**：
  1. `.side-dock` 改为 `top:0; bottom:0` 占满视口高度 + `justify-content:center` 真正垂直居中，**彻底不用 translateY**。
  2. 宽度限制 `left/right:0; width:52px` 只占屏幕一条窄带；`pointer-events:none` + `.side-dock > * { pointer-events:auto }` 保证不拦截页面其他区域点击。
  3. 视觉胶囊背景移到 `::before` 伪元素（`z-index:-1`），收起 `height:56px`，展开时用 CSS 变量 `--dock-open-height` 由 JS 动态贴合内容，避免铺满整屏。
  - JS 新增 `updateDockHeight(dock)`：按 `按钮数 × 按钮高 + 间距 + 把手高 + padding` 计算并写入 `--dock-open-height`，在 `setDockOpen()` 里调用。
- 防超出屏幕：`max-height: min(420px, calc(100vh - 120px))`，矮屏/窄屏 media query 同步为 `min(300px, calc(100vh - 100px))` / `min(260px, calc(100vh - 90px))`。
- 验证：4 脚本语法 OK；服务输出确认 `top:0/bottom:0/justify-content:center`；无残留实际 translateY（注释文字与气泡定位属正常用法）。

## 🔴 修侧边栏「按钮乱飞」最终版：残留 fixed 偏移值才是真凶（前两次都修错了）
- **装了 agent-browser 实测才定位成功**（`npm i -g agent-browser` + `agent-browser install` Chromium 155，然后用 `agent-browser eval` 读 `getBoundingClientRect`）。纯靠读 CSS 推断连续修错两次。
- **实测数据（修前）**：视口高 565，左栏展开后按钮 top 分别是 126 / **-16** / 100 / 216 —— 顺序错乱且有按钮跑到视口外。
- **真凶1：按钮带着原 fixed 定位的偏移值**。这些按钮原本是 `position:fixed; left:22px; bottom:-220px`（或 top/right），我改成 `position:relative` 后**那些 bottom/top 值依然生效**，把按钮往上拽。
  - 实测 `getComputedStyle` 确认残留：`top:-22px / -220px / -154px / -88px`、`left:22px`、`bottom:22px/220px/...`。
  - 修复：收纳态样式里显式 `top:auto !important; right:auto !important; bottom:auto !important; left:auto !important; transform:none; margin:0; flex:0 0 auto;`。
- **真凶2：`.floating-button` 自带 `button-breathe` 动画**（含 `translateY(-3px)`），在 flex 布局里干扰测量。修复：收纳态 `animation:none !important`，呼吸效果改由**父容器** `.side-dock-items` 承担（`dock-items-breathe`，整组上下浮动 5px），视觉上保留了漂浮感但不影响子元素定位。
- **真凶3（隐藏元凶）**：`.side-dock` 自己带 `background: rgba(15,23,42,.42)` + 铺满 `top:0;bottom:0` → 形成一条**通高 565px 的深色色带**，视觉上就是"面板乱飞/一大块黑条"。修复：`.side-dock` 设为 `background:transparent; border:none; box-shadow:none`，纯定位容器，可见胶囊只由 `::before` 提供（`z-index:-1` 去掉，改用正常层级 + 容器 `z-index:38`）。
- **收起态占位**：`max-height:0 + gap` 会让把手偏下。改成 `.side-dock-items { display:none }` → `.open { display:flex }`，收起时完全不占位，把手严格居中。
- **踩坑：浏览器缓存旧 CSS** 导致前两次修完测出来还是老样式。必须用 `store.html?v=<时间戳>` 强制刷新再测，否则白测。
- **最终实测结果**：左栏展开 4 按钮 top = 151/207/257/307（间距均匀 50px，全部 inView）；右栏 2 按钮 top = 211/261，全部 inView；展开一侧另一侧自动收起（互斥正常）；收起态把手 top=262 对视口 565 正好居中。截图确认视觉正常。
- **方法论教训（重要）**：这类"元素位置乱飞"问题，**必须用真实浏览器量 `getBoundingClientRect` 和 `getComputedStyle`**，不要只读 CSS 推断。我这次靠推断连修两次都错，浏览器实测一次就定位到残留 `top:-220px` 这种一眼看不出的问题。以后遇到布局异常，第一步就装浏览器量数据。
